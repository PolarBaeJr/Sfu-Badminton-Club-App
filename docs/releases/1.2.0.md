# Release 1.2.0

1.2.0 brings the club to phones. It adds native member apps for Android (Kotlin and Jetpack Compose) and iPhone (Swift and SwiftUI), and the website routes they need: passkey sign-in that returns session tokens, the association files that let an app use the club's passkeys and links, and bearer-token routes for challenges and check-in. It builds on 1.1.0 and adds no database migrations.

## For members

### The apps

- Native apps for Android (9 or later) and iPhone (iOS 17 or later), not wrappers around the website.
- Dark only, in the website's look: its colours, type, red brand tile and a shuttle app icon.
- Tabs: Feed, Leaderboard, Challenges, Stats and Membership (your fee statement).
- My stats shows only the active season's matches, as on the website.
- Links to those website pages can open in the app; other pages open in the browser.

### Feed

- The apps open on a Feed like the website's: the week strip, what is up next, club notices and club activity.
- Sessions fold into the Feed; a link to `/feed` or `/sessions` opens it at the linked session.
- A scan button on the Feed for the door code.

### Sign-in and account

- Sign in with an emailed code. Accounts are still created on the website, where the waivers are.
- Android: sign in with a passkey you already use on the website. Adding a passkey stays on the website.
- The session is stored encrypted on the phone (Android Keystore, iOS Keychain) and refreshed quietly.
- With no network, sign-in says "Could not reach the club server" instead of a raw error.

### Challenges

- See your challenges, start one with an opponent picker, and accept, reject or cancel.
- Submit, confirm or dispute results, and report walkovers.
- Every action goes through the website, so the same waiver, standing and feature checks, notifications and emails apply.

### Check-in and QR

- Scan a check-in or challenge QR code with the phone's camera.
- Show your own member QR code.
- A door QR or check-in link asks "Check in to this session?" and checks you in only when you tap Check in.

## For execs and admins

- No console changes. The console stays on the web; the apps are for members only.

## Under the hood

### Security and auth

- New `POST /api/passkey/app/login/options` and `/verify`: the signed challenge travels in the body as a `challengeToken`, and verify returns the Supabase session tokens in the body with no cookie.
- The app routes accept the web origin, `https://<rpId>` (for iOS) and one Android signing-certificate origin per configured fingerprint. The web routes still accept only the web origin.
- Web and app challenges are signed with different types, so neither is accepted by the other's route. Each challenge is single-use.
- Both verify routes share one implementation (`lib/passkey/login-assertion.ts`); the web route's behaviour is unchanged and pinned by a new route test.
- The apps never write to PostgREST directly. Reads use the member's own token, so row level security still applies.
- A link alone never checks anyone in, because any app can open the `sfubadminton://` scheme.

### APIs and services

- `GET /.well-known/assetlinks.json` and `GET /.well-known/apple-app-site-association`, built from runtime environment and answering 404 when unset. Both skip the middleware, because neither verifier follows a redirect.
- The Apple file carries `webcredentials` (passkeys) and `applinks` (universal link paths, kept in step with both apps' link routers).
- `POST /api/app/actions/<name>` runs the website's own server actions (challenges, match results, walkovers, check-in by token) as the member the bearer token belongs to.
- `GET /api/app/challenges/context` returns the standing, feature switch, rules, quota and opponent list the Challenges screens need.
- New error code `NET-003`: an app shows it when the website it reaches does not yet serve these routes.

### Database migrations

- None.

### The apps

- Android: Kotlin, Jetpack Compose, application id `com.sfubadminton.app`, minSdk 28, compileSdk and targetSdk 36. About 1.9 MB to download (unsigned release build).
- iOS: Swift and SwiftUI, Swift 6, no third-party dependencies, an XcodeGen project. A port of the Android app with the same calls, error codes and copy; about 0.8 MB zipped (unsigned Release archive).
- Both talk to GoTrue and PostgREST directly; no Supabase SDK.
- Rules they need from `packages/shared` (season filtering, auth errors, the club clock, fee statement and more) are hand-ported to Kotlin and Swift. The Elo engine is not ported: ratings are only read.
- Until universal links work, the iOS app also answers its own `sfubadminton://` URL scheme, for development and testing.
- An earlier Expo (React Native) version was dropped for download size and memory use.

## Before you deploy / owner steps

1. **No migrations** to apply for this release. 1.1.0's migrations must already be applied.
2. **Passkey trust, player service:** set `PASSKEY_ANDROID_CERT_SHA256` to every signing-certificate SHA-256 fingerprint an installed app can carry (debug, upload key, and Play App Signing), comma-separated. Set `PASSKEY_ANDROID_PACKAGE` only if the id is not `com.sfubadminton.app`. Staging first. No rebuild is needed: these are read at runtime.
3. **iOS, once there is an Apple team:** enrol in the Apple Developer Program, register the App ID `com.sfubadminton.app` with Associated Domains, set the team and entitlements file in the app's local config, and set `PASSKEY_IOS_APP_IDS` (`TEAMID.com.sfubadminton.app`) on the player service. The full list is in `apps/mobile/ios/README.md`.
4. **Check the association files** are served directly through the public entrance: `curl -i` both `/.well-known/` files on sfubadminton.com and expect `200`, `Content-Type: application/json` and no `Location` header. If the passkey RP ID host and the site host differ, check both. See `docs/ops/native-app-passkeys.md`.
5. **Edge rate limit:** add the pending `/api/app` limit (240 requests a minute) on both hosts when the player image with these routes deploys, then move it into the live table in `docs/ops/rate-limits.md`. Passkey app routes already sit under the `/api/passkey` limit.
6. **App builds:** Android reads the Supabase URL, anon key and `badminton.siteUrl` from `local.properties`; without the site URL it offers no passkey sign-in. iOS reads its local config, which `ios/scripts/config-from-android.sh` can write from the Android file.
7. **Store release:** a Google Play Console account and release signing for Android, and the Apple Developer account for iOS. Signing keys never go in this repo.
8. **Version, check:** the root `package.json` on this branch still reads `1.1.0`, and the Android app is `versionName 0.1.0`, `versionCode 1`. Bump before release.

## Known limitations

- The club has no Apple Developer account yet, so the iOS app cannot be signed for a device: passkey sign-in and universal links on iPhone wait on it. Email-code sign-in works.
- The iOS app has run only in the simulator. The Android app runs on the emulator against staging; its restyled signed-in screens have not been checked on a real device.
- The native iOS passkey origin (`https://<rpId>`) comes from Apple's documentation and has not been checked against a real assertion.
- Neither app is on the Play Store or App Store yet.
- Not in the apps yet: Google sign-in, tournament entry, receipt upload (done on the website), the tournament points ladder, realtime updates and push notifications.
- The apps show the fee statement to every approved member, even when the fees switch is off on the website.
- There is no minimum-version gate yet, and every future migration has to stay compatible with app versions already installed.
- The hand-ported Kotlin and Swift rules have no check that they stay in step with `packages/shared`.
- Passkeys cannot be added from the apps; members enrol them on the website.
