## Phase 3 — Backend API Endpoints

**Objective:** Build all API endpoints needed by both apps. Every endpoint must
follow the existing API conventions (REST resource naming, error response format,
status codes, auth middleware chain, input validation library).

### 3.1 — Sessions Endpoints

**POST /api/sessions**
- Admin only.
- Body: `{ title, date, start_time, end_time, location, description? }`
- Validation: title required, date must not be in the past, start_time before
  end_time, location required.
- Creates session with status `upcoming`, `check_in_open: false`.
- Sets `created_by` from the authenticated admin's ID.
- Returns the created session.

**GET /api/sessions**
- Accessible to both admins and players.
- Query params: `status` (filter by status), `from_date`, `to_date`, `limit`, `offset`.
- Default: returns all upcoming sessions ordered by date ASC, limit 20.
- For player requests: omit `check_in_token` from response.
- For admin requests: include all fields.

**GET /api/sessions/:id**
- Accessible to both admins and players.
- Includes attendance count (`verified_count`, `checked_in_count`) for admins.
- Omits `check_in_token` for player requests.

**PATCH /api/sessions/:id**
- Admin only.
- Allows updating: `title`, `date`, `start_time`, `end_time`, `location`,
  `description`, `status`.
- If `status` is set to `cancelled`, require `cancellation_reason` in body.
  Set `cancelled_at` to now().
- If check-in is currently open and session is being cancelled, automatically
  close check-in (set `check_in_open: false`, `check_in_closed_at: now()`).
- If `date`, `start_time`, or `end_time` is changed while check-in is open,
  return a 409 conflict error with message: "Cannot change session time while
  check-in is open. Close check-in first."
- Attendance records persist even if a session is cancelled.

**DELETE /api/sessions/:id**
- Admin only.
- Only allowed if session has zero attendance records. If attendance exists,
  return 409 with message: "Session has attendance records. Cancel it instead
  of deleting it."
- Hard deletes the session row.

### 3.2 — Check-In Endpoints

**POST /api/sessions/:id/check-in/open**
- Admin only.
- Session must have status `upcoming`.
- Generates a cryptographically secure random token (use `crypto.randomBytes(32)`
  or equivalent, hex-encoded). Stores it in `check_in_token`.
- Sets `check_in_open: true`, `check_in_opened_at: now()`.
- Returns: `{ check_in_token, qr_payload }` where `qr_payload` is a JSON string
  of `{ session_id, token }` — this is what gets encoded into the QR code on the
  frontend.

**POST /api/sessions/:id/check-in/close**
- Admin only.
- Sets `check_in_open: false`, `check_in_closed_at: now()`, nullifies
  `check_in_token`.
- Returns updated session.

**POST /api/sessions/:id/attend**
- Player only.
- Body: `{ token }` — the token decoded from the QR code.
- Validation steps (execute in this order, fail fast):
  1. Session exists.
  2. Session status is `upcoming`.
  3. `check_in_open` is `true`.
  4. Provided token matches `check_in_token` exactly (constant-time comparison).
  5. Player has not already checked in (UNIQUE constraint on session_id + player_id).
- On success: insert attendance row with `check_in_method: 'qr_scan'`,
  `verification_status: 'checked_in'`.
- Returns: `{ success: true, message: "You're checked in!", session_title, checked_in_at }`
- On duplicate check-in: return 409 with `{ already_checked_in: true }` — do not
  treat this as a hard error on the frontend; show a friendly message.

**POST /api/sessions/:id/attendance**
- Admin only. Manual attendance add.
- Body: `{ player_id, notes? }`
- Does not require check-in to be open.
- Inserts attendance row with `check_in_method: 'manual'`,
  `verification_status: 'verified'` (manual = already verified by an admin).
- Returns the attendance row.

**DELETE /api/sessions/:id/attendance/:player_id**
- Admin only.
- Hard deletes the attendance row.
- Returns 204.

**PATCH /api/sessions/:id/attendance/:player_id**
- Admin only.
- Allows updating: `verification_status`, `flag_reason`, `notes`.
- Sets `verified_by` and `verified_at` when status is changed to `verified`.
- Returns updated attendance row.

### 3.3 — Club Fee Endpoints

**GET /api/players/:player_id/fees**
- Admin only.
- Returns full payment history for the player, ordered by `paid_at` DESC.
- Includes a computed `current_season_status` field:
  - `"paid"` if a payment exists for the current active season.
  - `"unpaid"` if no payment exists for the current active season.

**POST /api/players/:player_id/fees**
- Admin only.
- Body: `{ amount, paid_at, season, payment_method, reference?, notes? }`
- Validation: amount must be positive, season must be a valid season code,
  paid_at must not be in the future.
- Sets `recorded_by` from authenticated admin's ID.
- Returns the created payment record.

**PATCH /api/players/:player_id/fees/:fee_id**
- Admin only. For corrections only.
- Allows updating: `amount`, `paid_at`, `season`, `payment_method`, `reference`,
  `notes`.
- Sets `updated_by` and `updated_at`.
- Appends an immutable audit note in `notes` in the format:
  `"[Edited by {admin_name} on {timestamp}] "` prepended to existing notes.
- Returns updated payment record.

**DELETE /api/players/:player_id/fees/:fee_id**
- Admin only.
- Soft-deletes by adding a `"[Deleted by {admin_name} on {timestamp}]"` note and
  setting a `deleted_at` field. Do not hard delete payment records.
- Returns 204.

**GET /api/players/fee-summary**
- Admin only.
- Returns a list of all players with their current season fee status.
- Shape: `[{ player_id, name, email, current_season_status, last_payment_date,
  last_payment_amount }]`
- Supports `status` query param: `paid`, `unpaid` for filtering.

## Phase 7 — Edge Cases, Guard Rails & Audit Trail

These are not optional. Each item must be implemented.

### Session State Guards

- A `cancelled` session cannot have its status changed back to `upcoming` or
  `completed` via the API. Return 422 if attempted.
- A `completed` session cannot have check-in opened.
- Sessions cannot be edited to a date in the past if they are in `upcoming` status.
  Return a warning (not a block) if an admin edits a session to a date in the past
  and it is still `upcoming`.

### Attendance Guards

- A player cannot check in to a cancelled session. The QR token validation checks
  session status before checking the token.
- A player cannot check in more than once to the same session. The UNIQUE constraint
  handles this at the DB level; the API must also handle it gracefully (see Phase 3
  attend endpoint).
- If an admin tries to manually add a player who is already in the attendance list,
  return 409. Do not silently ignore.

### Fee Audit Trail

- Payment edits must always produce an audit entry. The `notes` field is used for
  this (see Phase 3 PATCH endpoint). This is a lightweight but real audit trail.
- Voided payments must never be hard-deleted. If a `DELETE /api/players/:id/fees/:fee_id`
  request is received, soft-delete only.

### Token Security

- The check-in token must be generated with `crypto.randomBytes(32)` (or equivalent
  in the backend's language). Do not use `Math.random()` or UUIDs for security tokens.
- Token comparison must use a constant-time comparison function to prevent timing
  attacks. In Node.js: `crypto.timingSafeEqual(Buffer.from(a), Buffer.from(b))`.
- The token must be cleared (set to null) when check-in is closed, even if the
  session is cancelled mid-check-in.

### QR Code Hijacking Prevention

The session-scoped token (rather than a rotating time-based token) is used here
because rotating tokens are impractical in a sports hall environment. However,
the following must be enforced to prevent sharing:

1. The QR payload contains only `{ session_id, token }` — no player-specific data.
2. If the same player scans twice, return `already_checked_in: true`, not an error.
   This is friendly UX for genuine users and provides no additional info to an
   attacker.
3. Admin can see check-in timestamps. If two players checked in within milliseconds
   of each other using the same session, that is suspicious and worth flagging.
   The attendance list shows timestamps — no automated flagging needed unless the
   club requests it.
4. Admin verification (`verified` status) is the final control layer. The QR is
   first-pass; admin is ground truth.
